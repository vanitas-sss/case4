# Backend Марии: запуск, проверка и задачи команды

Дата: 11 ноября 2026. Ветка: `feat/maria-monitoring-completion`.

## 1. Что готово

В `main` уже были FastAPI, модели SQLite, миграции Alembic, приём отчётов и GET API.
Эта доработка завершает базовый цикл мониторинга:

- время получения отчёта используется для heartbeat, время из JSON — для метрик и порядка снимков;
- повторные и запоздавшие снимки не затирают новые данные;
- фоновая проверка сохраняет в историю как успешные проверки, так и простой;
- offline alert создаётся после `OFFLINE_AFTER + ALERT_AFTER_OFFLINE` без новых дублей и закрывается после восстановления;
- остановленный контейнер создаёт `container_stopped`; `running` закрывает тревогу;
- карта возвращает статус сервера и контейнера из текущих данных; при потере связи контейнер имеет `unknown`;
- `POST /import` загружает JSON-файл того же контракта, что `/ingest`;
- разрешены запросы из локального Vite, включены WAL и ожидание блокировки SQLite;
- операции фонового мониторинга и очистки работают в отдельном потоке со своей сессией БД, ошибки записываются в журнал;
- версии прямых зависимостей закреплены в `backend/requirements.txt`.

Формат существующих GET API и структура таблиц сохранены. Новых миграций не требуется.
Алерты и события видны в API; Telegram, произвольные HTTP/TCP проверки и редактор правил в этот прототип не входят.
Настоящий агент собирает команда кейса 1. Наша команда использует `mock-data/`.
Frontend и Docker Compose пока отсутствуют: запуск ниже проверяет backend и генератор, готового сайта ещё нет.

## 2. Как идут данные

`mock-data/generator.py → POST /api/v1/ingest → проверка ReportIn → SQLite → GET /api/v1/... → frontend`

Backend и frontend не читают Python-файлы друг друга. Их общий язык — HTTP и JSON.
Главные источники формата: `backend/app/schemas/ingest.py`, `backend/examples/ingest.example.json`, `docs/API_V1.md`.

| Данные | Значение |
|---|---|
| `source_id` + `host.name` | Вместе определяют сервер. Имена могут повторяться у разных источников |
| `timestamp` | Время снимка; предпочтительно ISO 8601 UTC с `Z`. Для следующего обновления должно увеличиваться |
| `host.status` | Состояние со слов источника; heartbeat может ухудшить его после таймаута |
| `last_seen` в GET | Время получения нового снимка backend, а не время внутри файла |
| `cpu_percent`, `memory_percent`, `disk_percent` | Числа 0–100 или `null`, если метрики нет |
| `net_rx_bytes`, `net_tx_bytes` | Накопительные счётчики байтов, не скорость и не проценты |
| `containers[].id` | ID контейнера у источника; в GET есть отдельный числовой ID базы |
| `network.nodes`, `network.links` | Снимок графа. Концы связей должны существовать в nodes |
| `accepted`, `rejected`, `errors` | Результат обработки отчётов; HTTP 200 сам по себе не означает, что все приняты |

Повтор с тем же timestamp принимается без дублирования данных и не продлевает heartbeat.
Импорт старого, но нового для этого сервера снимка устанавливает время получения на сейчас: это проверка связи с отправителем, а не доказательство актуальности старых метрик.

## 3. Запуск на Windows PowerShell

Установить Git и Python 3.11 или 3.12. SQLite входит в Python; отдельный сервер БД и Docker для этого запуска не нужны.
Если репозиторий уже скачан, начните с `cd case4` и `git fetch origin`.

```powershell
git clone https://github.com/vanitas-sss/case4.git
cd case4
git fetch origin
git switch feat/maria-monitoring-completion
cd backend
py -3.11 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.venv\Scripts\python.exe -m alembic upgrade head
.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

Если Python 3.12 установлен вместо 3.11, замените `py -3.11` на `py -3.12`.
Команды вызывают Python напрямую из venv: активировать окружение и менять ExecutionPolicy не требуется.
`Copy-Item` выполняйте только при первом запуске: существующий `.env` с личными настройками сохраняйте.
Миграции также автоматически выполняются при старте. Рабочий каталог должен быть `backend`.
Используйте один процесс Uvicorn: несколько `--workers` запустят несколько одинаковых фоновых проверок.

Открыть Swagger: http://127.0.0.1:8000/docs
Проверка процесса: http://127.0.0.1:8000/api/v1/health

## 4. Запустить генератор

Откройте второй PowerShell в корне `case4`:

```powershell
cd mock-data
py -3.11 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe generator.py --url http://127.0.0.1:8000/api/v1/ingest --interval 5
```

Он отправляет отчёты раз в 5 секунд. Не запускайте одновременно сценарий и второй обычный генератор для тех же серверов.
Прочитайте `/hosts`, возьмите реальный `id` сервера и проверьте:

| Адрес в Swagger | Ожидаемый результат |
|---|---|
| `GET /hosts` | Серверы генератора с процентами нагрузки |
| `GET /hosts/{id}` | Карточка с контейнерами |
| `GET /hosts/{id}/metrics?period=1h` | История метрик, не более 500 точек |
| `GET /containers` | Контейнеры из отчётов |
| `GET /topology` | Узлы и связи; каждый конец связи есть среди узлов |
| `GET /summary` | Счётчики серверов, контейнеров и алертов |
| `GET /availability?period=24h` | Доля успешных проверок, `null` при отсутствии истории |
| `GET /events` | Изменения статусов и алертов |
| `GET /alerts?status=active` | Активные тревоги |

Все адреса таблицы имеют префикс `/api/v1`.

## 5. Проверить отказ и восстановление

При скопированном `.env.example`: `WARNING_AFTER=10`, `OFFLINE_AFTER=20`, `ALERT_AFTER_OFFLINE=10`, `CHECK_PERIOD=5`.
Без `.env` действуют более длинные значения из `config.py`: 120/150/10/30 секунд.

1. Дайте генератору поработать 15 секунд и остановите его `Ctrl+C`.
2. Через 10 секунд после последнего отчёта сервер станет warning; через 20 — offline. Фоновый цикл может добавить до 5 секунд задержки.
3. Через 30–35 секунд появится одна активная тревога `host_offline` для каждого замолчавшего сервера.
4. У карты сервер offline, у его контейнеров unknown: отсутствие связи не доказывает остановку контейнера.
5. Повторяйте GET: новых одинаковых активных тревог не должно быть, uptime будет снижаться.
6. Запустите генератор снова. После свежего отчёта статус online, тревога resolved, появляется событие восстановления.

Для проверки CPU и контейнера остановите генератор, возьмите пример JSON в Swagger `POST /ingest`, поставьте текущий `timestamp`, CPU=95 и статус контейнера `stopped`.
Будут `cpu_high` и `container_stopped`. Отправьте следующий снимок с большим timestamp, CPU=40 и контейнером `running`: обе тревоги закроются.
CPU проверяется по одному снимку, порог >=90%, выдержка времени для CPU не реализована.
`target` контейнерной тревоги — строка с числовым ID контейнера базы, имя контейнера есть в message.

В `POST /import` выберите файл `backend/examples/ingest.example.json`. Ожидается `accepted=1`, `rejected=0`.
Повторная загрузка не создаёт второй сервер или метрику. Файл максимум 2 МиБ, кодировка UTF-8, верхний уровень — массив.
Произвольный JSON кейса 1 автоматически не распознаётся. Для него нужен реальный пример и согласованный адаптер.

## 6. Автоматические проверки

Третий терминал, из корня проекта:

```powershell
cd backend
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m alembic check
```

Тесты используют временные базы, не удаляют рабочие метрики. CI проверяет Python 3.11 и 3.12.
Один успешный прогон не гарантирует отсутствие любых ошибок; перед демонстрацией нужна проверка всего пути с готовым frontend.

## 9. Совместимость и ограничения

- Не менять поля JSON без согласования с frontend и генератором. `/ingest` принимает массив, не объект с ключом `ingest_request`.
- На общей карте ID имеют префикс `host_id:`, например `1:frontend`. При фильтре `host_id` ID локальные. Считайте ID непрозрачными строками и используйте ссылки из того же ответа.
- Vite: либо proxy `/api` на `http://127.0.0.1:8000`, либо базовый URL API с портом 8000. CORS по умолчанию разрешён только для localhost/127.0.0.1:5173.
- Для другого адреса задайте `CORS_ORIGINS=["http://адрес:порт"]` в `.env` и перезапустите backend.
- Uptime — доля успешных периодических проверок (online), а не точное измерение времени работы. Старые записи из прежнего ingest могут влиять на показатель до очистки истории.
- Пустой список контейнеров сохраняет ранее известные контейнеры. Полный снимок с удалением исчезнувших контейнеров пока не поддерживается.
- Храним историю 7 дней, очищаем раз в час. Период проверки 5 секунд удобен для демонстрации; 30 секунд снижает число записей для длительного запуска.
- Backend рассчитан на учебный стенд и один процесс. Аутентификации нет; перед публичным размещением нужен отдельный этап защиты и ограничений запросов.
- Не удаляйте рабочую БД для обновления: используйте Alembic. Не добавляйте `.env`, `.venv`, БД и токены в Git.
- Если порт 8000 занят, задайте Uvicorn `--port 8001` и замените порт в URL генератора и frontend.
- Если данные не обновляются, проверьте accepted/rejected/errors и увеличение timestamp. После изменения `.env` перезапустите backend.
