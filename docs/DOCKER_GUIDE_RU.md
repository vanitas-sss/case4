# Запуск и проверка системы в Docker

Команды выполняются в PowerShell из корня репозитория `case4`, где находится `compose.yaml`. Локальные Python, Node.js и `.venv` для Docker-запуска не нужны. Нужны Git и работающий Docker Desktop в режиме Linux containers с Docker Compose v2. На Linux подходят Docker Engine и Compose plugin.

## Получить изменения

До слияния pull request:

```powershell
cd C:\Users\User\case4
git fetch origin
git switch --track origin/feat/frontend-integration
```

Если локальная ветка уже создана, используйте `git switch feat/frontend-integration`, затем `git pull --ff-only`. Сохраните свои незакоммиченные изменения перед переключением; не используйте принудительный сброс.

После слияния вместо этого можно использовать `git switch main` и `git pull --ff-only`.

## Запустить с демонстрационными данными

```powershell
docker version
docker compose version
docker compose --profile demo config --quiet
docker compose --profile demo up --build -d --wait
docker compose --profile demo ps
```

Первая сборка скачивает образы и зависимости. Должны появиться backend, frontend и generator. Backend и frontend должны стать `healthy`, generator — работать (`Up`).

Откройте:

- http://localhost:8080 — интерфейс;
- http://localhost:8000/docs — Swagger;
- http://localhost:8080/api/v1/health — ответ `{"status":"ok"}` через nginx;
- http://localhost:8000/api/v1/health — тот же ответ напрямую от backend.

Миграции применяются автоматически при старте backend. SQLite хранится в именованном Docker volume `case4_monitoring-data`, а не в Windows `.venv`. Внутри контейнера файл расположен по пути `/data/metrics.db`.

Генератор каждые 5 секунд отправляет синтетические данные: это не нагрузка вашего компьютера. На чистой базе после первого успешного отчёта появятся 3 сервера и 11 контейнеров. Если ранее были импорты, объектов будет больше. Показатели CPU/RAM/диска меняются в пределах демонстрационного сценария. История строится с момента отправки данных, поэтому сразу после запуска график может содержать лишь одну точку.

## Что должно отображаться

| Страница | Что проверить |
|---|---|
| Обзор | Число серверов и контейнеров, график CPU/RAM, доступность и последние события |
| Серверы | server-01, server-02, server-03; поиск по имени/IP/source_id; статусы |
| Карточка сервера | Источник, время сигнала и измерения, последние значения, история и события только этого сервера |
| Контейнеры | Названия, образы, хосты, состояния, IP и сети в панели |
| Метрики | Выбор сервера или всех узлов, CPU/RAM/диска, периодов 1h/6h/24h/7d |
| События | Тип, сервер и сообщение; серверный фильтр периода и типа, поиск среди последних 500 результатов |
| Топология | Узлы и связи, фильтр сервера, выбор узла и список связей |
| Источники | source_id принятых отчётов, число серверов и импорт JSON |
| Тревоги | Активные тревоги в верхней части страницы; текст причины и сервер |

`API доступен` означает успешный запрос health, а не отсутствие тревог или работоспособность всех агентов. Прочерк означает отсутствие данных, а не ноль. Доступность рассчитывается по фоновым проверкам backend, не по времени работы ОС.

## Проверить остановку и восстановление источника

Оставьте backend и frontend работающими:

```powershell
docker compose --profile demo stop generator
```

От последнего сигнала:

1. Примерно через 10 секунд статус серверов станет «Задержка».
2. Примерно через 20 секунд — «Нет связи».
3. Примерно через 30 секунд backend создаст тревогу `host_offline`.
4. Контейнеры станут «Нет данных»: недоступный сервер не доказывает, что контейнер остановился.

Проверка backend идёт каждые 5 секунд, интерфейс тоже обновляется периодически, поэтому возможна небольшая задержка отображения.

```powershell
docker compose --profile demo start generator
```

После нового отчёта серверы вернутся в сеть, тревоги потери связи закроются, появятся события восстановления. Проверьте также:

```powershell
Invoke-RestMethod http://localhost:8080/api/v1/alerts?status=active
Invoke-RestMethod http://localhost:8080/api/v1/alerts?status=resolved
```

## Проверить отсутствие backend

```powershell
docker compose stop backend
```

После следующего опроса интерфейс должен показать «Нет связи с API» и ошибки загрузки. Он не подменяет ответы вымышленными данными. При недоступном backend nginx может отвечать 502.

```powershell
docker compose start backend
```

Дождитесь восстановления соединения. При пересоздании backend nginx обновляет Docker DNS, поэтому адрес контейнера не зафиксирован навсегда.

## Импортировать собственный JSON

Во вкладке «Источники» выберите файл в UTF-8 до 2 МиБ и нажмите «Загрузить отчёты». Верхний уровень должен быть массивом, даже если отчёт один. Пример: `backend/examples/ingest.example.json`.

У примера фиксированная историческая дата. Для проверки текущих графиков создайте отдельный файл с текущей датой:

```powershell
$reports = Get-Content .\backend\examples\ingest.example.json -Raw | ConvertFrom-Json
$reports[0].timestamp = [DateTime]::UtcNow.ToString("o")
$reports[0].source_id = "manual-test"
$reports[0].host.name = "manual-server"
$json = ConvertTo-Json -InputObject @($reports) -Depth 20
[System.IO.File]::WriteAllText((Join-Path $PWD "manual-report.json"), $json, [System.Text.UTF8Encoding]::new($false))
```

Импорт должен показать `Принято: 1. Отклонено: 0`. Сервер `manual-server` появится в таблице. Поскольку это разовая отправка, через некоторое время он станет недоступным — это ожидаемо.

Для проверки валидации поставьте `cpu_percent: 150`. Результат должен содержать отклонённый отчёт и причину. В массиве из правильного и неправильного отчётов правильный сохраняется, неправильный отклоняется.

Повтор одного и того же отчёта может вернуть `accepted: 1`, но не должен создавать новую метрику. Новый timestamp создаёт новое измерение. Старые отчёты не заменяют более новые.

## Запустить без демонстрационного генератора

```powershell
docker compose --profile demo stop generator
docker compose up --build -d --wait
```

На новой базе страницы будут пустыми. Это нормальный результат до подключения агента или импорта. Существующие записи из volume сохраняются.

Агент с компьютера отправляет массив отчётов на `http://localhost:8080/api/v1/ingest`. Контейнер генератора использует `http://backend:8000/api/v1/ingest` внутри Compose-сети. Произвольный JSON от других систем автоматически не преобразуется: нужен согласованный контракт.

## Тесты

Backend в контейнере:

```powershell
docker compose exec backend python -m pytest -q
```

Тесты используют временные базы и не должны изменять рабочую SQLite.

Frontend при установленном Node.js 22:

```powershell
cd frontend
npm ci
npm run lint
npm run format:check
npm test
npm run build
cd ..
```

Полный браузерный прогон запускайте на отдельном тестовом Compose-проекте и чистой базе. Сначала остановите обычный проект, чтобы освободить порты:

```powershell
docker compose --profile demo down
docker compose -p case4-e2e up --build -d --wait
cd frontend
npx playwright install chromium
npm run test:e2e
cd ..
docker compose -p case4-e2e down -v
docker compose --profile demo up -d --wait
```

E2E-тесты создают специальные тестовые хосты, проверяют пустую базу, страницы, импорт, ошибки связи и таймауты. Поэтому не запускайте их на рабочем стенде с данными. `down -v` в примере удаляет только volume проекта `case4-e2e`.

В GitHub Actions workflow `Frontend and Docker integration` проверяет сборку всех образов, браузерные сценарии через nginx, генератор и сохранность данных после перезапуска backend. В артефакте `browser-report` доступны отчёт, снимки страниц и trace при ошибке.

## Остановка, данные и логи

```powershell
docker compose --profile demo logs --tail 100
docker compose --profile demo down
```

`down` останавливает контейнеры, но сохраняет базу. Для обычной остановки не добавляйте `-v`: этот параметр удаляет volume с данными.

Если порт занят, остановите ранее запущенные Vite/Uvicorn или другой Compose-проект. Если `docker version` показывает только Client и ошибку подключения, запустите Docker Desktop и дождитесь готовности Engine. Ошибки скачивания образов связаны с доступом к реестрам: проверьте подключение и повторите сборку.

## Ограничения

- Система наблюдает за инфраструктурой. Управление серверами и контейнерами, токены агентов и пользовательская авторизация не реализованы.
- CPU/RAM отдельных контейнеров, аптайм ОС и число перезапусков не входят в текущий контракт; интерфейс не выдумывает их.
- История метрик хранится 7 дней. График отдельного узла содержит выборку до 500 точек; инфраструктуры — усреднение сначала внутри узла, затем между узлами за интервалы. Частые отчёты одного узла не увеличивают его вес. Это среднее процентов, не среднее с учётом мощности серверов.
- В журнале максимум 500 последних событий по фильтрам. Это не счётчик всех событий за период.
- Топология доступна для просмотра. Ручное редактирование и экспорт PlantUML не входят в эту интеграцию.
- Порты по умолчанию открыты только на localhost. Для общего сервера отдельно нужны HTTPS, авторизация и правила доступа.
