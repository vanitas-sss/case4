# Архитектура проекта

Backend построен по слоистой схеме: API принимает запросы, сервисы выполняют сценарии приложения, репозитории работают с базой данных, а модели описывают её структуру.

## Структура backend

```text
backend/
├── app/
│   ├── api/v1/          # HTTP-маршруты и обработка запросов
│   ├── core/            # настройки и общие утилиты
│   ├── db/              # подключение, сессии и инициализация БД
│   ├── models/          # SQLAlchemy-модели таблиц
│   ├── repositories/    # запросы и операции с БД
│   ├── schemas/         # проверка входящих данных
│   ├── services/        # логика обработки данных
│   ├── workers/         # фоновые задачи
│   ├── main.py          # создание FastAPI-приложения
│   └── stubs.py         # демонстрационные данные для API
└── tests/               # тесты API и работы с БД
```

## За что отвечает каждый слой

- **API (`api/v1`)** — принимает HTTP-запросы, вызывает нужный сервис и формирует ответ. Здесь не должно быть сложных запросов к базе.
- **Schemas (`schemas`)** — проверяют структуру и значения входящих данных. Это граница между внешним JSON и внутренним кодом.
- **Services (`services`)** — связывают операции в единый сценарий. Например, `ingest_service` сохраняет хост, метрики, контейнеры, доступность и топологию одного отчёта.
- **Repositories (`repositories`)** — содержат запросы к конкретным таблицам. Они используют переданную SQLAlchemy-сессию и не фиксируют транзакцию самостоятельно.
- **Models (`models`)** — описывают таблицы и связи между ними.
- **DB (`db`)** — создаёт подключение и управляет сессиями.
- **Core (`core`)** — общие настройки и небольшие утилиты, которые используются в нескольких слоях.
- **Workers (`workers`)** — задачи, которые могут выполняться отдельно от HTTP-запросов, например очистка старой истории.

## Как проходит ingest-запрос

1. Агент или генератор отправляет массив JSON-отчётов на `POST /api/v1/ingest`.
2. API проверяет каждый элемент через схему `ReportIn`.
3. Валидный отчёт передаётся в `ingest_service.process`.
4. Сервис вызывает репозитории и сохраняет связанные записи в одной транзакции.
5. При успешном сохранении транзакция фиксируется. При ошибке выполняется rollback, а API учитывает отчёт как отклонённый.
6. Ответ содержит количество принятых и отклонённых отчётов.

## Важные договорённости

- Формат входящих данных задаётся в `contracts/api-examples.json`. Изменения контракта нужно согласовывать с командой.
- Репозитории вызывают `flush()`, но не делают `commit()`: транзакцией управляет сервис.
- Время перед сохранением в SQLite приводится к UTC.
- Новые HTTP-маршруты размещаются в `api/v1`, а не в `main.py`.
- Логика не должна дублироваться в маршрутах и репозиториях.

## Чтение данных и фоновые задачи

GET-маршруты `hosts`, `containers`, `topology`, `availability`, `events`, `alerts` и `summary` используют `app/services/dashboard_service.py`. Сервис читает SQLAlchemy-модели и преобразует их в обычные словари, которые FastAPI сериализует в JSON. Файл `app/stubs.py` оставлен как демонстрационный пример и больше не является источником данных для этих маршрутов.

`app/workers/monitor.py` содержит два фоновых цикла:
- проверка heartbeat раз в `CHECK_PERIOD`: меняет статус сервера на warning/offline, создаёт событие и offline alert;
- очистка старой истории раз в час через `cleanup_old_records`.

Базовый alerting выполняется в `app/services/alert_service.py`: CPU >= 90% и offline. После получения нового отчёта состояние тревоги пересчитывается; восстановившаяся тревога переводится в resolved.

## Ограничения текущей реализации

- Telegram/webhook-уведомления не подключены.
- HTTP/TCP checks произвольных адресов и CRUD правил алертинга не реализованы.
- Ручное редактирование топологии и экспорт PlantUML не реализованы.
- Формат отчёта агента должен быть подтверждён интеграционным тестом на реальном JSON источника.
- Форматы ответов API документированы в `docs/API_V1.md`; frontend должен использовать их без прямого доступа к SQLite.
